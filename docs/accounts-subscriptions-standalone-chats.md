# Аккаунты, подписки и чаты без связки мессенджеров

Черновик решения. Повод: функция «видео из ссылок» (`Services/VideoEmbed`) ценна сама по
себе — пользователю может быть нужен один чат в одном мессенджере и никакой пересылки.
Сейчас же вся модель построена на том, что сначала связываются два мессенджера, и только
после этого появляются `accounts`, `chat_links` и что-либо полезное.

Документ отвечает на три вопроса: какой должна стать модель данных, как связывать
мессенджеры, если у каждой стороны уже есть своё нажитое (чаты, статистика, подписка),
и как это мигрировать.

---

## 1. Диагноз: где именно упирается текущая модель

1. **`accounts` рождается из связки.** Строка появляется в `UserRepository.LinkAccountsAsync`
   и умирает в `UnlinkAsync`. Значит, у одиночного пользователя нет вообще ничего, к чему
   можно прикрепить подписку, лимиты и статистику. Все таблицы, которые «вешаются на
   `account_id` с `ON DELETE CASCADE`», при разрыве связки исчезают — для статистики это
   было приемлемо, для оплаченной подписки это потеря денег.
2. **Аккаунт — это пара, а не владелец.** Отсюда и `UnlinkAsync` = `DELETE FROM accounts`.
   Пока аккаунт ничего не стоит, удалять его дёшево. Как только на нём висят деньги,
   удаление аккаунта при отвязке становится невозможно в принципе.
3. **Чат существует только внутри связки.** `chat_links` — это одна строка с двумя
   сторонами (`max_*`, `tg_*`), обе `NOT NULL`. Одиночный чат в эту таблицу не ложится.
   Настройка фичи (`video_embed_enabled`) висит на связке, хотя по смыслу это свойство
   чата — «в этом чате бот подставляет видео».
4. **`ChatLinkingService` жёстко требует связки аккаунтов**: репост из чата без
   `LinkedToUser` отвечает `chat_link_need_account_link` и не делает ничего. Это ровно тот
   вход, который теперь должен работать без связки.
5. **Мелкое, но всплывёт при слиянии:** `chat_links` уникальна по паре
   `(max_chat_id, tg_chat_id)`, то есть один и тот же чат может участвовать в нескольких
   связках, а `FindActiveByChatAsync` берёт `LIMIT 1` — какую именно, не определено.

---

## 2. Главное решение

> **Аккаунт создаётся при первом появлении пользователя, всегда. Связывание двух
> мессенджеров — это `merge` двух аккаунтов, а не создание нового. Разрыв — `split`.**

Смысловой сдвиг: `accounts` перестаёт быть «парой» и становится **владельцем/расчётной
единицей** — тем, к чему прикреплены 1..2 идентичности (`users`), чаты, настройки,
статистика, подписка. «Связаны ли мессенджеры» — это больше не `account_id IS NOT NULL`,
а «в моём аккаунте есть идентичность в другом мессенджере».

Что это сразу даёт:

- подписку и лимиты всегда есть куда положить, ещё до всякой связки;
- разрыв связки перестаёт быть удалением аккаунта — а значит, ничего оплаченного не
  сгорает каскадом;
- пересылка между мессенджерами становится **одной из функций** аккаунта, а не
  предусловием для всего остального;
- третий мессенджер (если появится) вписывается без переделки: просто третья идентичность.

> **Второе решение, без которого первое неполноценно:** чат становится самостоятельной
> строкой (`chats`), а `chat_links` — связью двух таких строк. Иначе одиночный чат негде
> хранить, а флаг фичи так и останется на связке, которой нет.

## 3. Схема БД

### 3.1 `accounts` — владелец

```sql
CREATE TABLE accounts (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at     TEXT    NOT NULL,
    state          TEXT    NOT NULL DEFAULT 'active',   -- 'active' | 'merged'
    merged_into_id INTEGER REFERENCES accounts(id),     -- куда влит, если state='merged'
    merged_at      TEXT
);
```

**Аккаунт не удаляется никогда** (кроме удаления самого пользователя по его требованию).
При слиянии проигравшая строка остаётся надгробием со ссылкой `merged_into_id`. Это нужно
не из любви к аудиту, а потому что во внешней платёжной системе могут остаться ссылки на
старый `account_id` (вебхук об оплате/возврате придёт спустя дни) — по надгробию мы всегда
дойдём до актуального аккаунта.

### 3.2 `users` — идентичность

Колонки остаются, меняются два правила:

```sql
-- account_id становится обязательным (после бэкфила) и больше не SET NULL
-- в аккаунте не может быть двух идентичностей одного мессенджера:
CREATE UNIQUE INDEX ux_users_account_messenger ON users (account_id, messenger);
```

`linked_to_user` **предлагаю упразднить.** Вторая сторона теперь ищется запросом
`SELECT * FROM users WHERE account_id = @id AND messenger <> @mine`. Держать вдобавок
явную ссылку — значит при каждом merge/split синхронизировать две вещи вместо одной,
и получить ровно ту «полусвязку», от которой защищались транзакцией. Переходный вариант:
оставить колонку, но перестать её читать, и снести отдельной миграцией позже.

### 3.3 `chats` — подключённый чат (новое)

```sql
CREATE TABLE chats (
    id                  INTEGER PRIMARY KEY AUTOINCREMENT,
    messenger           TEXT    NOT NULL,          -- 'tg' | 'max'
    chat_id             TEXT    NOT NULL,          -- id чата в мессенджере
    kind                TEXT    NOT NULL,          -- 'chat' | 'channel'
    title               TEXT    NOT NULL,
    account_id          INTEGER NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
    added_by_user_id    TEXT    NOT NULL,          -- кто подключил (в паре с messenger)
    active              INTEGER NOT NULL DEFAULT 1,
    video_embed_enabled INTEGER NOT NULL DEFAULT 1,
    created_at          TEXT    NOT NULL,
    UNIQUE (messenger, chat_id)
);
CREATE INDEX ix_chats_account ON chats (account_id);
```

`UNIQUE (messenger, chat_id)` — **глобальный**, а не в пределах аккаунта. Один чат
принадлежит одному аккаунту. Причины:

- иначе двое подключат один и тот же канал, и видео прилетит в него дважды, а квота
  спишется у обоих;
- слияние аккаунтов при глобальной уникальности не может породить дубликат чата — просто
  потому, что дубликата не было и до слияния;
- заодно чинится нынешняя неопределённость с `LIMIT 1` в `FindActiveByChatAsync`.

Цена: второму пользователю, подключающему занятый чат, надо честно ответить «этот чат уже
подключён другим пользователем». На будущее — передача владения по подтверждению правами
администратора чата; сейчас достаточно понятного отказа.

### 3.4 `chat_links` — связь двух чатов

```sql
CREATE TABLE chat_links (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    max_chat    INTEGER NOT NULL REFERENCES chats(id) ON DELETE CASCADE,
    tg_chat     INTEGER NOT NULL REFERENCES chats(id) ON DELETE CASCADE,
    active      INTEGER NOT NULL DEFAULT 1,
    title       TEXT    NOT NULL,
    repost_type TEXT    NOT NULL,
    created_at  TEXT    NOT NULL,
    UNIQUE (max_chat, tg_chat)
);
CREATE UNIQUE INDEX ux_chat_links_max ON chat_links (max_chat);
CREATE UNIQUE INDEX ux_chat_links_tg  ON chat_links (tg_chat);
```

Из таблицы уезжают: `*_chat_id`, `*_chat_type`, `*_user_id`, `*_chat_title`, `account_id`,
`video_embed_enabled` — всё это теперь свойства чата. Остаётся только то, что описывает
именно связь: направление, активность, заголовок.

Имена колонок оставляю `max_chat`/`tg_chat`, а не абстрактные `a`/`b`: весь код (`RepostDirection`,
`TargetChatId`, статистика) сегодня рассуждает в терминах MAX↔TG, и переход на нейтральные
имена — отдельная задача, которую разумно делать в тот день, когда появится третий
мессенджер, а не сейчас.

Два `UNIQUE` по одной стороне — сознательное ограничение «чат участвует максимум в одной
связке». Оно упрощает пересылку (никаких ветвлений «в какой из связанных чатов») и
соответствует нынешнему фактическому поведению. Если позже понадобится веерная рассылка
1→N, эти индексы снимаются, а `FindActiveByChatAsync` возвращает список.

### 3.5 Статистика

`relay_stats` меняется минимально: `chat_link_id` заменяется на `chat_id` (id строки
`chats`, из которой сообщение ушло), `account_id` остаётся денормализацией для быстрых
выборок.

```sql
CREATE TABLE relay_stats (
    account_id INTEGER NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
    chat_id    INTEGER NOT NULL,      -- исторический id chats, без FK (как и раньше)
    day        TEXT    NOT NULL,
    direction  TEXT    NOT NULL,
    ...
    PRIMARY KEY (account_id, chat_id, day, direction)
);
```

Почему по чату, а не по связке: **статистика должна ездить вместе с чатом.** При merge и
split чаты переходят между аккаунтами, и правило «строка статистики принадлежит тому же
аккаунту, что и её чат» даёт однозначный, механический перенос (`UPDATE relay_stats SET
account_id = ... WHERE chat_id IN (...)`). Со связкой такого правила не построить: связка
при split вообще перестаёт существовать.

Отсутствие FK на `chat_id` — по той же причине, что и раньше (см. комментарий в `M009`):
`ON DELETE SET NULL` сломал бы `ON CONFLICT`, так как NULL в SQLite не равны друг другу.

### 3.6 Потребление квот (новое)

Видео-функция расходует внешний ресурс, значит её надо считать отдельно от объёма
пересылки:

```sql
CREATE TABLE usage_counters (
    account_id INTEGER NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
    period     TEXT    NOT NULL,      -- 'YYYY-MM', UTC
    kind       TEXT    NOT NULL,      -- 'video_embed'
    used       INTEGER NOT NULL DEFAULT 0,
    updated_at TEXT    NOT NULL,
    PRIMARY KEY (account_id, period, kind)
);
```

Правило учёта: **одна скачка = одна единица**, независимо от того, в сколько чатов видео
потом опубликовали. Считается на аккаунт владельца чата-источника. Проверять лимит нужно
до постановки задачи во внешний сервис (`VideoEmbedRelayService.TryRelayInBackground`),
а инкремент делать после успешного скачивания — иначе очередь на сервисе съедает квоту
за неудачи.

Приятный побочный ход: кэш `url → уже скачанный файл` за последние N часов экономит и
квоту, и внешний сервис — в общих чатах одну и ту же ссылку кидают повторно.

### 3.7 Подписка

```sql
-- Витрина: то, что читает горячий путь и мини-приложение.
CREATE TABLE subscriptions (
    account_id INTEGER PRIMARY KEY REFERENCES accounts(id) ON DELETE CASCADE,
    plan       TEXT    NOT NULL,      -- 'free' | 'pro' | ...
    paid_until TEXT,                  -- NULL для free
    updated_at TEXT    NOT NULL
);

-- Источник правды: журнал выданных периодов.
CREATE TABLE billing_grants (
    id                  INTEGER PRIMARY KEY AUTOINCREMENT,
    account_id          INTEGER NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
    owner_messenger     TEXT    NOT NULL,   -- кому принадлежит грант: идентичность,
    owner_user_id       TEXT    NOT NULL,   -- а не аккаунт (см. §5.2)
    plan                TEXT    NOT NULL,
    days                INTEGER NOT NULL,
    amount_minor        INTEGER NOT NULL DEFAULT 0,   -- копейки; 0 = промо/подарок
    currency            TEXT,
    external_payment_id TEXT UNIQUE,        -- идемпотентность вебхука платёжки
    status              TEXT    NOT NULL,   -- 'active' | 'refunded' | 'void'
    granted_at          TEXT    NOT NULL,
    starts_at           TEXT    NOT NULL,   -- рассчитанное окно действия
    ends_at             TEXT    NOT NULL
);
CREATE INDEX ix_billing_grants_account ON billing_grants (account_id, status);
```

`subscriptions.paid_until` — **производная величина**, а не самостоятельный факт: она
пересчитывается из активных грантов укладкой окон встык (`starts_at` очередного гранта =
`max(now, конец предыдущего)`). Именно это делает слияние аккаунтов тривиальным: перенёс
гранты — пересчитал витрину. Если хранить только `paid_until`, при merge придётся
изобретать арифметику над двумя числами, потерять историю и не суметь корректно обработать
возврат платежа.

## 4. Что покупается: аккаунт или чат

Развилка, от которой зависит вся дальнейшая монетизация. Коротко:

| | Подписка на аккаунт (+квоты) | Лицензия на чат/связку |
|---|---|---|
| UX и оплата | одна кнопка, понятно | «за какой чат я плачу?» |
| Merge аккаунтов | нужно правило сложения сроков | ничего не сливается, лицензии просто переезжают с чатами |
| Split | нужно правило дележа | лицензия уходит с чатом |
| Монетизация каналов | слабее | сильнее (за каждый канал платят) |

**Рекомендую подписку на аккаунт с квотами** (число подключённых чатов, число связок,
видео в месяц). Причины: покупка — одно действие, статистика и лимиты уже привязаны к
аккаунту, а расход у видео-функции пропорционален не числу чатов, а числу скачиваний.
Проблема merge при этом решается журналом грантов (§5.2) и не является поводом уходить в
лицензии.

Если позже захочется лицензий на чат — они ложатся поверх той же схемы: `billing_grants`
получает необязательный `chat_id`, и грант действует не на весь аккаунт, а на один чат.
Ломать ничего не придётся.

## 5. Процедуры

### 5.1 Регистрация и подключение чата (новый основной сценарий)

1. Пользователь пишет боту `/start` или открывает мини-приложение → `users.UpsertAsync`
   в той же транзакции заводит `accounts` и `subscriptions(plan='free')`. Аккаунт есть
   всегда, дальше по коду он `NOT NULL` и никаких `if (AccountId is { })`.
2. Пользователь добавляет бота в чат/канал и репостит оттуда сообщение боту → создаётся
   строка `chats` на его аккаунт. **Связка мессенджеров не требуется.** Видео-функция
   начинает работать немедленно.
3. Ответ бота: «Чат подключён, видео из ссылок включено. Хотите зеркалить сообщения между
   MAX и Telegram — свяжите второй мессенджер: /link». Сейчас на этом месте отказ
   (`chat_link_need_account_link`) — его надо заменить.
4. Если чат уже занят другим аккаунтом — отказ с объяснением.

`ChatLinkingService.HandleRepostAsync` при этом расщепляется на два шага: «подключить чат»
(всегда) и «создать связку, если у второй стороны того же аккаунта есть ожидающий выбор»
(как сегодня). Поле `users.linking_chat_*` остаётся ровно для второго шага.

### 5.2 Связывание мессенджеров = merge

Вход: идентичность A (инициатор, ввёл код) и идентичность B (владелец кода), у каждой свой
аккаунт `accA`, `accB`.

**Предусловие.** Если в `accA` уже есть идентичность того же мессенджера, что и B (или
наоборот) — прямой merge невозможен: в аккаунте не может быть двух Telegram-аккаунтов.
Это сегодняшний сценарий «связаться, уже будучи связанным». Порядок: сначала явный split
старой пары с предупреждением пользователю («вы уже связаны с …, старая связка будет
разорвана»), потом merge. Молча рвать — плохо: у старого партнёра могут быть чаты и
оплаченный период.

**Выбор выжившего.** Детерминированно, в этом порядке:
1. аккаунт с более поздним `paid_until` (у кого «дороже» подписка);
2. при равенстве — аккаунт с бо́льшим числом чатов;
3. при равенстве — более старый `created_at`.

Смысл — минимизировать объём переносимого и не потерять внешние ссылки платёжки на
активную подписку.

**Транзакция merge (одна, целиком):**
```
UPDATE users          SET account_id = survivor WHERE account_id = loser;
UPDATE chats          SET account_id = survivor WHERE account_id = loser;
UPDATE relay_stats    SET account_id = survivor WHERE account_id = loser;
UPDATE usage_counters SET account_id = survivor WHERE account_id = loser;  -- со сложением по PK
UPDATE billing_grants SET account_id = survivor WHERE account_id = loser;
DELETE FROM subscriptions WHERE account_id = loser;
-- пересчёт subscriptions(survivor) из billing_grants
UPDATE accounts SET state='merged', merged_into_id=survivor, merged_at=... WHERE id=loser;
```
`usage_counters` переносится не голым `UPDATE` (упрётся в первичный ключ при совпадении
периода), а `INSERT ... ON CONFLICT DO UPDATE SET used = used + excluded.used` с
последующим удалением исходных строк. Квоты складываются — иначе связывание аккаунтов
обнуляло бы расход и стало бы способом обойти лимит.

**Слияние подписок.** Гранты обеих сторон складываются в один журнал и укладываются
встык: оплаченные периоды суммируются, никто ничего не теряет. Если планы разные —
действует высший план, а дни низшего конвертируются по отношению цен
(`days_pro = days_basic * price_basic / price_pro`, округление вниз в пользу пользователя
можно заменить на вверх, это уже вопрос щедрости). Это честнее, чем «берём максимум из
двух `paid_until`», где вторая оплата просто сгорает.

**Связки чатов при merge не создаются автоматически.** После слияния у аккаунта появляется
набор чатов MAX и набор чатов Telegram, но какой с каким зеркалить — знает только человек.
Мини-приложение должно предложить это явно: список чатов с кнопкой «связать с…».

### 5.3 Разрыв связки = split

Аккаунт **не удаляется**. Уходящая идентичность получает новый пустой аккаунт, и на него
переезжает то, что принадлежит ей.

```
INSERT INTO accounts ... -> newAcc
UPDATE users  SET account_id = newAcc WHERE account_id = old AND messenger = @leaving;
UPDATE chats  SET account_id = newAcc WHERE account_id = old AND messenger = @leaving;
UPDATE relay_stats SET account_id = newAcc WHERE chat_id IN (чаты уходящей стороны);
DELETE FROM chat_links WHERE max_chat/tg_chat принадлежат разным аккаунтам;  -- связка распалась
UPDATE billing_grants SET account_id = newAcc
    WHERE account_id = old AND owner_messenger = @leaving;   -- гранты едут к плательщику
-- пересчёт subscriptions обоих аккаунтов
```

**Правило дележа подписки:** грант принадлежит той идентичности, которая его оплатила
(`owner_*`), и уезжает вместе с ней. Аккаунт — лишь контейнер, где грант в данный момент
учитывается. Это самое простое правило, которое одновременно:

- справедливо — уносишь ровно то, что купил;
- не создаёт денег из воздуха — гранты не копируются, а перераспределяются;
- не требует спрашивать пользователя «кому оставить подписку».

Промо-гранты выдавать тоже с указанием идентичности, а не «аккаунту» — иначе при split они
повиснут без правила.

`usage_counters` при split **не делятся** — расход остаётся на старом аккаунте, новый
начинает с нуля за текущий период. Точный дележ потребовал бы учёта расхода по чатам;
выигрыш нулевой, а «связался-развязался» не должен обнулять квоту (см. §6).

Симметричность разрыва (вызов с одной стороны рвёт всю пару) сохраняется — это удобное
свойство сегодняшнего кода, менять его не нужно.

### 5.4 Что происходит с чатами и связками

- Одиночный чат живёт сам по себе, связка — надстройка над двумя чатами.
- Удаление связки **не** удаляет чаты: видео-функция в них продолжает работать. Сегодня
  «удалить связку» = потерять всё; это придётся развести в мини-приложении на два разных
  действия: «разорвать зеркалирование» и «отключить чат».
- Отключение чата (`DELETE FROM chats`) каскадом сносит связку — и это правильно.

## 6. Инварианты, которые нельзя нарушать

1. **Аккаунт с историей платежей не удаляется никогда.** Только `state='merged'` со
   ссылкой. Любой `DELETE FROM accounts` в коде после этой переделки — ошибка.
2. **Гранты не копируются.** Ни при merge, ни при split. Иначе цикл «связал — развязал»
   становится клонированием подписки. Это первое, что попробует любой, кто разберётся в
   механике.
3. **Квоты при merge складываются, при split не возвращаются.** Иначе связывание-разрыв —
   способ обнулить месячный расход.
4. **Один чат — один аккаунт** (`UNIQUE (messenger, chat_id)`).
5. **В аккаунте максимум одна идентичность на мессенджер** (`UNIQUE (account_id, messenger)`).
6. **Merge и split — по одной транзакции каждый.** Ровно по той же причине, по какой
   сегодня целиком транзакционен `LinkAccountsAsync`: половинчатое состояние выглядит для
   остального кода нормальным и ломает логику молча.
7. **Идемпотентность платежей** — по `billing_grants.external_payment_id UNIQUE`. Вебхуки
   платёжных систем повторяются, это нормальный режим их работы.

## 7. План миграций

Порядок важен: `M011` можно катить отдельно и сразу, `M012` — самая тяжёлая.

**M011 — «Аккаунт всем»**
- `accounts`: `+state`, `+merged_into_id`, `+merged_at`;
- бэкфил: каждому `users` без `account_id` — свой новый аккаунт;
- `CREATE UNIQUE INDEX ux_users_account_messenger`;
- перестроить `users` так, чтобы `account_id` был `NOT NULL` и без `ON DELETE SET NULL`.

**M012 — `chats` + перестройка `chat_links`**
- создать `chats`;
- на каждую строку `chat_links` — две строки `chats` (перенести `*_chat_id`, `*_chat_type`,
  `*_chat_title`, `*_user_id → added_by_user_id`, `account_id`, `video_embed_enabled`
  копируется обеим сторонам);
- если один и тот же чат встречался в нескольких связках (см. §1.5) — оставить первую по
  `created_at`, остальные связки записать в лог и удалить; такие случаи надо просмотреть
  глазами до выката;
- пересоздать `chat_links` в новом виде и перелить.

**M013 — статистика**: `relay_stats.chat_link_id → chat_id` с переносом значений через
карту «старая связка → чат-источник по направлению»; `usage_counters`.

**M014 — биллинг**: `subscriptions`, `billing_grants`. Можно катить позже остальных, когда
дойдёт до оплаты.

### Технический нюанс SQLite

`MigrationRunner` выполняет каждую миграцию в транзакции, а `SqliteConnectionFactory`
включает `PRAGMA foreign_keys = ON` на соединении. Перестройка таблицы с внешними ключами
(create new → copy → drop → rename) при включённых FK внутри транзакции не пройдёт, а
`PRAGMA foreign_keys` **внутри транзакции не действует** — это надо знать заранее. Рабочий
приём: первой строкой такой миграции выполнить `PRAGMA defer_foreign_keys = ON;` — он
работает внутри транзакции и откладывает проверку до `COMMIT`. Перед коммитом полезно
прогнать `PRAGMA foreign_key_check;` и упасть, если что-то не сошлось: лучше не стартовать,
чем стартовать с битыми ссылками.

И, поскольку миграции необратимы: перед первым запуском новой версии — копия файла БД.
`M012` — не та миграция, которую хочется откатывать вручную.

## 8. Что придётся тронуть в коде

- `UserRepository`: `LinkAccountsAsync` → `MergeAccountsAsync`, `UnlinkAsync` →
  `SplitAccountAsync`; `UpsertAsync` заводит аккаунт; поиск второй стороны — по
  `account_id`, а не по `linked_to_user`.
- Новый `ChatRepository` (подключение/отключение чата, поиск по `(messenger, chat_id)`,
  список по аккаунту, тумблеры фич). `ChatLinkRepository` худеет до собственно связей.
- `ChatLinkingService`: репост без связки аккаунтов больше не отказ, а подключение чата.
- `MessageRelayService`: `FindRelayableLinkAsync` идёт через `chats`; `RecordStats` уже не
  нуждается в проверке `link.AccountId is { }` — аккаунт есть всегда.
- `VideoEmbedRelayService`: работает от **чата**, а не от связки. Логика публикации:
  видео уходит в чат-источник, если у него включён флаг, и в связанный чат, если он есть,
  активен и флаг включён у него. Сегодняшняя семантика «флаг один на связку» меняется на
  «флаг у каждого чата» — это заметно пользователю, стоит упомянуть в списке изменений.
  Плюс проверка квоты перед постановкой задачи.
- Мини-приложение: экран «Мои чаты» (подключённые чаты с тумблерами) появляется до и
  независимо от связки; «Связки» становятся отдельным разделом; на стартовом экране связка
  мессенджеров — предложение, а не требование; статистика больше не отвечает `Linked=false`
  (аккаунт есть всегда, показываем то, что есть).
- Тексты в `Localization`: `chat_link_need_account_link` заменяется на «чат подключён,
  а зеркалирование — по желанию»; новые тексты про занятый чат, про замену старой связки,
  про сложение оплаченных периодов при слиянии.

Порядок работ, если делать поэтапно: **M011 + правки аккаунтов** (безопасно, пользователю
незаметно) → **M012/M013 + `chats` + одиночная видео-функция** (то, ради чего всё
затевалось) → **M014 + биллинг** (когда дойдут руки до оплаты).

## 9. Отвергнутые варианты

- **Оставить `chat_links` и добавить отдельную таблицу «одиночных чатов».** Два источника
  правды об одном и том же («чат подключён, вот его настройки»), флаг `video_embed_enabled`
  в двух местах, и в каждом запросе — `UNION`. Дешевле сегодня, дороже через месяц.
- **Сделать стороны `chat_links` nullable.** Одиночный чат как «полусвязка». Каждая
  выборка обрастает `IS NULL`-ветками, а связывание одиночного чата с другим превращается
  в мутацию строки вместо создания новой сущности. Плюс `UNIQUE (max_chat_id, tg_chat_id)`
  с NULL перестаёт работать: в SQLite NULL не равны друг другу, и дубликаты полезут.
- **При merge запрещать связку, если у обоих активная подписка.** Честно, но пользователь
  упирается в стену ровно в тот момент, когда он уже заплатил дважды. Сложение периодов
  решает это без разговоров.
- **При merge брать максимум из двух `paid_until`.** Просто, но это молчаливое сжигание
  чужих денег.
- **При split спрашивать пользователя, кому достанется подписка.** Диалог, в котором
  стороны не согласны друг с другом, разрешить нечем. Правило «уносит плательщик» не
  требует ничьего согласия.

## 10. Открытые вопросы

1. **Тарифицируем аккаунт или чат?** (§4). От этого зависит, нужен ли `billing_grants.chat_id`
   с самого начала. Моя рекомендация — аккаунт с квотами.
2. **Что входит в бесплатный план?** Конкретно: сколько видео в месяц, сколько чатов,
   доступна ли пересылка. Пока фича включена всем по умолчанию (`M010`, `DEFAULT 1`), и
   вводить лимит задним числом на живых пользователях неприятно — лучше определиться до
   первой платной версии.
3. **Передача владения чатом.** Что делать, если чат подключил один админ, а бота
   настраивает другой. На старте достаточно отказа «чат занят», но вопрос вернётся.
4. **Удаление аккаунта по требованию пользователя** (в связке с §6.1) — нужен явный
   сценарий: что стирается, что остаётся обезличенным.
5. **Возврат платежа** после merge: грант помечается `refunded`, `paid_until`
   пересчитывается — надо решить, уведомляем ли обе стороны объединённого аккаунта.
