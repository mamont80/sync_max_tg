# SyncMax

Бот-мост между мессенджерами **MAX** и **Telegram**. Один процесс поднимает сразу два бота.

> **Этап 1:** связывание аккаунтов из двух мессенджеров через 6-значный код.
> **Этап 2:** связывание чатов/каналов (добавление бота в группу или команда `/link`).
> **Этап 3 (текущий):** пересылка сообщений между связанными чатами. Пока только текст.

## Требования

- .NET 10 SDK
- Visual Studio 2026 (решение `SyncMax.sln`)

## Как это работает (связывание)

1. Пользователь отправляет `/start` любому из ботов.
2. Бот регистрирует пользователя в SQLite и присылает приветствие с **6-значным кодом**.
   Код бессрочный — действует, пока не будет использован (или перевыпущен повторным `/start`).
3. Пользователь открывает **второй** бот и вводит этот код.
4. Второй бот находит владельца кода в другом мессенджере и создаёт связь
   `tg ↔ max`. Оба получают подтверждение.

Неважно, какой мессенджер связывать с каким — направление роли не играет.

Попытки ввода кода троттлятся — не чаще одной принятой в обработку попытки
раз в 2 секунды на пользователя (защита от перебора, так как код бессрочный).

## Как это работает (связывание чатов)

Доступно только уже связанным между собой аккаунтам (см. выше) — иначе бот
предлагает сначала пройти связывание по коду.

1. Чат/канал выбирается либо в момент добавления бота в него, либо (если бот
   уже был добавлен раньше) сообщением `/link`, отправленным в этом чате.
   Бот определяет чат, его тип (`chat`/`channel`) и название, и запоминает
   этот выбор за пользователем, который добавил бота или отправил `/link`.
2. Бот просит сделать то же самое во втором мессенджере — связанный аккаунт
   должен так же добавить бота в нужный чат или отправить там `/link`.
3. Как только оба выбора сделаны, создаётся активная связка чатов, а оба
   пользователя получают подтверждение с её названием: `{чат1} <=> {чат2}`.

Направление пересылки сообщений (`repost_type`) пока всегда `both` (в обе стороны).

## Как это работает (пересылка сообщений)

Как только между чатами есть активная связка (`chat_links`, `active = 1`),
`MessageRelayService` пересылает в связанный чат каждое сообщение (кроме `/link`),
пришедшее в один из связанных чатов, — если направление (`repost_type`) это
разрешает. Сообщение предваряется служебной «шапкой» с именем отправителя и
меткой источника, а сам текст/подпись идёт с новой строки:

```
👤 {Имя} · (из TG)
{текст}
```

Сообщения, отправленные самим ботом (в т.ч. пересланные им же), не
обрабатываются повторно — иначе связка при направлении `both` зациклилась бы.

### Медиа

Пересылаются фото, видео, голос, аудио, анимации, «кружки» (video_note) и файлы
(документы). Всё, что можно, отправляется «родным» типом целевой платформы;
текст сообщения переносится как подпись к первому вложению.

- **Приём.** `*BotService` скачивает вложение во **временный файл на диске**
  (не в ОЗУ): Telegram — через `getFile`/download (лимит Bot API — 20 МБ на
  скачивание), MAX — GET по прямому `url` из вложения. Результат — платформо-
  независимый `RelayMessage` (подпись `FormattedText` + список `MediaAttachment`).
- **Отправка.** Целевой клиент кодирует по-своему: Telegram — родными
  `SendPhoto/Video/Voice/Audio/Animation/VideoNote/Document`; MAX — через
  upload-flow (`POST /uploads` → загрузка бинарника полем `data` → прикрепление
  по `token`/`photos`), с повторами на `400`, пока сервер обрабатывает файл.
- **Временные файлы** удаляются `MessageRelayService` после отправки (в любом исходе).

Соответствие типов для MAX (там нет анимаций/кружков/голоса как отдельных типов):
фото → `image`, видео/анимация/video_note → `video`, голос/аудио → `audio`,
документ → `file`.

**Конвертация** разрешена для аудио и фото, но не для видео (`MediaConverter`,
внешний ffmpeg, путь — `Media:FfmpegPath`). Сейчас используется для перекодирования
голоса в mp3. Если ffmpeg не найден или конвертация не удалась — файл уходит как
есть. **Универсальный откат:** если «родная» отправка вложения не удалась, оно
пересылается как обычный файл/документ (для MAX — `type=file`, для Telegram —
`SendDocument`).

Крупные вложения ограничены `Media:MaxFileMegabytes` (по умолчанию 45 МБ; для
Telegram фактический потолок скачивания всё равно 20 МБ — ограничение платформы).

### Ответы (reply)

Если пересылаемое сообщение — ответ на другое, пересланная копия оформляется как
ответ на пересланную копию оригинала. Для этого на каждую пересылку сохраняется
соответствие «id оригинала ↔ id копии» в таблице `message_links` (обе стороны).
При пересылке ответа `MessageRelayService` находит по этой карте копию исходного
сообщения в целевом чате и проставляет reply: Telegram — `ReplyParameters`,
MAX — `link{type:"reply", mid}`. Если оригинал не найден в карте (отправлен до
связки/фичи) — сообщение пересылается как обычное, без оформления ответа.
Ограничение: для голоса/аудио MAX (см. выше про пустой `message_created`) id
недоступен, поэтому ответы на такие сообщения пока не переносятся.

### Редактирование и удаление

Правки и удаления переносятся на пересланную копию через ту же карту `message_links`
(отдельная таблица не нужна) — `MessageRelayService.RelayEditAsync` / `RelayDeleteAsync`.

- **Правка.** Меняется текст, а у медиа — подпись (само медиа не заменяется). Приём:
  Telegram — апдейт `edited_message` (добавлен в `allowedUpdates`), MAX — `message_edited`.
  Отправка: Telegram — `EditMessageText`/`EditMessageCaption`; MAX — `PUT /messages`, причём
  чтобы правка подписи не стёрла вложение, текущие вложения дотягиваются через
  `GET /messages?message_ids=` и переотправляются по `token`. У MAX окно редактирования
  ограничено по времени — по его истечении правка не применится (ошибка логируется).
- **Удаление.** Работает только **MAX → Telegram**: MAX присылает `message_removed`, и мы
  удаляем копию в Telegram (`DeleteMessage`) + чистим запись карты. Обратное направление
  невозможно — Telegram **не уведомляет** ботов об удалении сообщений пользователем.
- Собственные правки/удаления бота игнорируются (та же защита от эха по `_botId`), поэтому
  цикла не возникает.

### Форматирование

Разметка текста (жирный, курсив, подчёркнутый, зачёркнутый, моноширинный,
ссылки) переносится между платформами через платформо-независимую модель
`FormattedText` (чистый текст + список участков `TextSpan` с офсетами в UTF-16):

- **Приём.** Каждый `*BotService` конвертирует свой формат в `FormattedText`:
  Telegram — из `MessageEntity[]` (`TelegramFormatting`), MAX — из массива
  `markup` (`MaxFormatting`).
- **Отправка.** Целевой клиент кодирует `FormattedText` в свой формат:
  Telegram — обратно в entities (без `parse_mode`, без экранирования),
  MAX — в markdown-строку с `format: "markdown"` (спецсимволы экранируются).

Стили, у которых нет пары на другой стороне (spoiler/blockquote/mention у
Telegram; heading/highlighted/user_mention у MAX), при переносе отбрасываются —
текст остаётся, стиль теряется. Само форматирование по разметке (`FormattedText`)
не зависит от `*BotService`, как и весь `MessageRelayService`.

Сообщения от ботов вообще (не только от своего, но и от любых чужих ботов в
чате) не пересылаются — это решает каждый `*BotService` сам, до вызова
`MessageRelayService`, по данным конкретной платформы об отправителе
(`message.From.IsBot` в Telegram, `message.Sender.IsBot` в MAX — nullable,
т.к. неизвестно, всегда ли MAX присылает этот признак).

## Системные команды

Обрабатываются только в личном чате с ботом (не в группе/канале), в обоих
мессенджерах одинаково — логика вынесена в `SystemCommandService`.

- `/deleteAllLinks` — удаляет все связки чатов (`chat_links`), у всех пользователей.
- `/clear` — удаляет все связки чатов, а также связку аккаунтов и "ожидающий"
  выбор чата (`linked_to_user`, `linking_chat_id`, `linking_chat_type`,
  `linking_chat_title`) у обеих сторон связки, если аккаунты были связаны.
  Обеим сторонам приходит сообщение о сбросе настроек, а затем — новое
  приглашение связать аккаунты (как после `/start`).

## Ключи / токены

Оставлены пустыми в [`src/SyncMax/appsettings.json`](src/SyncMax/appsettings.json) — впишите свои:

```json
{
  "Telegram": { "Token": "ВАШ_TELEGRAM_BOT_TOKEN" },
  "Max":      { "Token": "ВАШ_MAX_BOT_TOKEN", "ApiBaseUrl": "https://platform-api2.max.ru" }
}
```

Токены можно не хранить в файле, а передать через переменные окружения
(перекрывают `appsettings.json`):

```
Telegram__Token=...
Max__Token=...
Database__ConnectionString=Data Source=syncmax.db
```

Если токен мессенджера пуст — соответствующий бот просто не запускается
(приложение работает, это удобно для локальной отладки одного из ботов).

## Запуск

```powershell
dotnet run --project src/SyncMax
```

## Логирование

Логи пишутся одновременно в **консоль** (стандартный провайдер хоста) и в **файл**
через собственный `FileLoggerProvider` (без внешних зависимостей). Файлы — в подпапке
`logs` рядом с бинарником, с ротацией по дням: `logs/syncmax-YYYY-MM-DD.log`.

Уровни берутся из секции `Logging:LogLevel` в `appsettings.json` (общие для консоли и
файла). При необходимости для файла можно задать отдельные уровни через алиас `File`,
например:

```json
"Logging": {
  "LogLevel": { "Default": "Information" },
  "File": { "LogLevel": { "Default": "Warning" } }
}
```

## База данных

SQLite, файл создаётся автоматически (по умолчанию `syncmax.db`).

**Таблица `users`** — по записи на каждый мессенджер:
`user_id` (open_id для MAX), `messenger` (`tg`/`max`), `registered_at`,
`is_active`, `name`, `language`, `link_code`, `link_code_created_at`,
`linked_to_user`, `linking_chat_id`, `linking_chat_type`, `linking_chat_title`.
Первичный ключ — пара (`user_id`, `messenger`). Индекс `ix_users_link_code` —
поиск по коду связки.

Связка аккаунтов хранится прямо в этой таблице: `linked_to_user` — `user_id`
связанного аккаунта в другом мессенджере, заполняется у обеих сторон связки.
`linking_chat_*` — "ожидающий" выбор чата для связки чатов (репост сделан
одной стороной, ждём вторую); очищается, как только связка создана.

**Таблица `chat_links`** — связки чатов/каналов между MAX и Telegram:
`max_chat_id`, `max_chat_type` (`chat`/`channel`), `max_user_id`,
`tg_chat_id`, `tg_chat_type`, `tg_user_id`, `active`, `title`
(`{чат1} <=> {чат2}`), `repost_type` (`max_to_tg`/`tg_to_max`/`both`,
сейчас всегда `both`), `created_at`. Уникальность по паре
(`max_chat_id`, `tg_chat_id`).

**Таблица `message_links`** — карта «оригинал ↔ пересланная копия» для переноса
ответов (reply): `max_chat_id`, `max_msg_id` (mid), `tg_chat_id`, `tg_msg_id`
(message_id), `created_at`. По одной записи на пересылку; индексы по обеим
сторонам — поиск копии работает в любом направлении.

### Миграции / версии схемы

Версия схемы хранится в `PRAGMA user_version` файла БД. При старте
`MigrationRunner` применяет все миграции с версией больше текущей в одной
транзакции каждая. Чтобы добавить изменение в будущем:

1. Создайте класс `M00X_Описание : IMigration` с бОльшим `Version`.
2. Зарегистрируйте его в `Program.cs` рядом с `M001_InitialSchema`.

Ничего вручную запускать не нужно — обновление происходит на старте.

## Структура

```
src/SyncMax/
  Program.cs                    — хост, DI, запуск миграций и ботов
  appsettings.json              — токены и настройки (ключи пустые)
  Configuration/                — классы опций
  Models/                       — User, MessengerType, ChatLink, ChatKind, RepostDirection,
                                   FormattedText (разметка), RelayMessage/MediaAttachment (медиа)
  Data/
    SqliteConnectionFactory.cs
    Migrations/                 — IMigration, MigrationRunner, M001..M003
    Repositories/               — UserRepository, ChatLinkRepository
  Services/                     — LinkingService, ChatLinkingService, MessageRelayService,
                                   SystemCommandService, MediaConverter, TempFiles,
                                   CodeGenerator, Localization
  Messengers/
    IMessengerApiClient.cs      — общий интерфейс клиента (отправка текста/медиа)
    Telegram/                   — TelegramApiClient (отправка), TelegramBotService (приём),
                                   TelegramFormatting (entities ↔ FormattedText)
    Max/                        — MaxApiClient (отправка), MaxBotService (приём), MaxModels,
                                   MaxFormatting (markup/markdown ↔ FormattedText)
```

## Заметки

- Отправка и приём разделены. `*ApiClient` (`MaxApiClient`, `TelegramApiClient`)
  реализуют общий интерфейс `IMessengerApiClient` и отвечают только за исходящие
  запросы к API (текст сейчас; фото/файлы/видео добавятся туда же по мере
  реализации). `*BotService` (`MaxBotService`, `TelegramBotService`) — фоновые
  сервисы, которые занимаются только long polling и разбором входящих
  обновлений; для отправки они не нужны никому, кроме себя самих.
- `LinkingService` не зависит ни от платформы, ни от `*BotService` — только от
  `IMessengerApiClient` (получает все реализации через DI и выбирает нужную по
  `MessengerType`). Добавление нового мессенджера = новый `*ApiClient`,
  реализующий `IMessengerApiClient`, плюс новый `*BotService` для приёма.
- DTO-модели MAX (`MaxModels.cs`) и `MaxApiClient` заполнены под типовой формат
  Bot API MAX (long polling). Если реальные эндпоинты/поля отличаются — правятся
  только эти два файла.
