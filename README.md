# SyncMax

Бот-мост между мессенджерами **MAX** и **Telegram**. Один процесс поднимает сразу два бота.

> **Этап 1:** связывание аккаунтов из двух мессенджеров через 6-значный код.
> **Этап 2:** связывание чатов/каналов (добавление бота в группу или команда `/link`).
> **Этап 3:** пересылка сообщений между связанными чатами (текст, медиа, правки, удаления).
> **Этап 4:** [мини-приложение](#мини-приложение) — общий веб-интерфейс управления
> связками для обоих мессенджеров.
> **Этап 5 (текущий):** [модерация](#модерация) пересылаемого текста — маскировка мата и
> блокировка запрещённого.

## Требования

- .NET 10 SDK
- Visual Studio 2026 (решение `SyncMax.sln`)
- `ffmpeg` в `PATH` — для конвертации аудио при пересылке (без него голосовые
  пересылаются файлом, остальное работает)

Либо только **Docker** — SDK и ffmpeg не нужны, см. [Запуск в Docker](#запуск-в-docker).

## Как это работает (связывание)

1. Пользователь отправляет `/start` любому из ботов.
2. Бот регистрирует пользователя в SQLite и присылает приветствие с **6-значным кодом**.
   Код бессрочный — действует, пока не будет использован (или перевыпущен повторным `/start`).
3. Пользователь открывает **второй** бот и вводит этот код.
4. Второй бот находит владельца кода в другом мессенджере и создаёт связь
   `tg ↔ max`. Оба получают подтверждение.

Неважно, какой мессенджер связывать с каким — направление роли не играет.

Попытки ввода кода троттлятся — не чаще одной принятой в обработку попытки
раз в 2 секунды на пользователя (защита от перебора, так как код бессрочный).

## Как это работает (связывание чатов)

Доступно только уже связанным между собой аккаунтам (см. выше) — иначе бот
предлагает сначала пройти связывание по коду.

1. Чат/канал выбирается либо в момент добавления бота в него, либо (если бот
   уже был добавлен раньше) сообщением `/link`, отправленным в этом чате.
   Бот определяет чат, его тип (`chat`/`channel`) и название, и запоминает
   этот выбор за пользователем, который добавил бота или отправил `/link`.
2. Бот просит сделать то же самое во втором мессенджере — связанный аккаунт
   должен так же добавить бота в нужный чат или отправить там `/link`.
3. Как только оба выбора сделаны, создаётся активная связка чатов, а оба
   пользователя получают подтверждение с её названием: `{чат1} <=> {чат2}`.

Связка создаётся с направлением `both` (в обе стороны) — см. [Направление пересылки](#направление-пересылки).

## Как это работает (пересылка сообщений)

Как только между чатами есть активная связка (`chat_links`, `active = 1`),
`MessageRelayService` пересылает в связанный чат каждое сообщение (кроме `/link`),
пришедшее в один из связанных чатов, — если направление (`repost_type`) это
разрешает. Сообщение предваряется служебной «шапкой» с именем отправителя и
меткой источника, а сам текст/подпись идёт с новой строки:

```
👤 {Имя} · (из TG)
{текст}
```

Если исходное сообщение само было **репостом**, добавляется вторая строка с источником —
без неё пересланная копия выглядит как собственное сообщение отправителя:

```
👤 Михаил Шумилов · (из TG)
↪️ Переслано из «Видео Инсайды»
{текст}
```

Название источника оформляется **ссылкой на оригинал**, когда её есть из чего построить.
Данные у платформ разные:

| Источник | Что известно | Ссылка |
|---|---|---|
| Публичный канал/чат Telegram | название и id сообщения | `t.me/{username}/{msg}` |
| Приватный канал/супергруппа Telegram | название и id сообщения | `t.me/c/{id}/{msg}` — откроется только у участников |
| Пользователь Telegram (в т.ч. скрытый) | имя | нет |
| Любой репост из MAX | только сам факт пересылки | нет |

У MAX в `link.forward` приходят лишь текст и вложения оригинала — ни исходного чата, ни
автора там нет, поэтому для него строка выглядит просто `↪️ Переслано`.

**Особенность MAX, из-за которой легко потерять сообщение:** при репосте он оставляет
собственное тело сообщения пустым (в `body` только `mid` и `text: ""`), а весь настоящий
контент — текст, разметку и вложения — кладёт в `link.message`. Читать содержимое репоста
нужно оттуда, иначе получается пустое сообщение, которое дальше отбрасывается как «нечего
пересылать». Идентификатор для карты «оригинал ↔ копия» при этом берётся всё равно из
`body.mid`: он указывает на сообщение в нашем чате, а не на оригинал в чужом.

Правки строку о репосте не восстанавливают: в апдейте правки платформы сведения об
источнике не повторяют.

Сообщения, отправленные самим ботом (в т.ч. пересланные им же), не
обрабатываются повторно — иначе связка при направлении `both` зациклилась бы.

### Направление пересылки

Направление хранится в `chat_links.repost_type` и принимает три значения:

| Значение | Что переносится |
|---|---|
| `both` (по умолчанию) | в обе стороны |
| `max_to_tg` | только из MAX в Telegram |
| `tg_to_max` | только из Telegram в MAX |

Направление соблюдается **для всех типов переноса одинаково** — обычного сообщения
с текстом и медиа, правки и удаления. Например, при `max_to_tg` правка сообщения в
Telegram на копию в MAX не поедет, как не поехало бы и само сообщение.

Так же строго проверяется и **активность связки** (`active = 1`): у деактивированной
не переносится ничего, включая правки и удаления сообщений, пересланных раньше, —
записи в `message_links` сами по себе права на перенос не дают.

Сменить направление у существующей связки можно пока только правкой `repost_type`
в БД — команды для пользователя ещё нет. Новые связки всегда создаются как `both`.

### Медиа

Пересылаются фото, видео, голос, аудио, анимации, «кружки» (video_note) и файлы
(документы). Всё, что можно, отправляется «родным» типом целевой платформы;
текст сообщения переносится как подпись к первому вложению.

- **Приём.** `*BotService` скачивает вложение во **временный файл на диске**
  (не в ОЗУ): Telegram — через `getFile`/download (лимит Bot API — 20 МБ на
  скачивание), MAX — GET по прямому `url` из вложения. Результат — платформо-
  независимый `RelayMessage` (подпись `FormattedText` + список `MediaAttachment`).
- **Отправка.** Целевой клиент кодирует по-своему: Telegram — родными
  `SendPhoto/Video/Voice/Audio/Animation/VideoNote/Document`; MAX — через
  upload-flow (`POST /uploads` → загрузка бинарника полем `data` → прикрепление
  по `token`/`photos`), с повторами на `400`, пока сервер обрабатывает файл.
  Тело ответа на загрузку **обязательно только для изображений** (там приходит
  `photos`-map с токенами); для видео и аудио токен берётся из ответа `/uploads`, а сам
  CDN на успешную загрузку видео отвечает HTML-страницей. Поэтому не-JSON в ответе
  загрузки не считается ошибкой: иначе видео откатывалось бы на отправку документом.
  Ответ `/uploads` пишется в лог — по нему видно, есть ли токен.
- **Временные файлы** удаляются `MessageRelayService` после отправки (в любом исходе).

Соответствие типов для MAX (там нет анимаций/кружков/голоса как отдельных типов):
фото → `image`, видео/анимация/video_note → `video`, голос/аудио → `audio`,
документ → `file`.

**Конвертация** разрешена для аудио и фото, но не для видео (`MediaConverter`,
внешний ffmpeg, путь — `Media:FfmpegPath`). Сейчас используется для перекодирования
голоса в mp3. Если ffmpeg не найден или конвертация не удалась — файл уходит как
есть. **Универсальный откат:** если «родная» отправка вложения не удалась, оно
пересылается как обычный файл/документ (для MAX — `type=file`, для Telegram —
`SendDocument`).

Крупные вложения ограничены `Media:MaxFileMegabytes` (по умолчанию 45 МБ; для
Telegram фактический потолок скачивания всё равно 20 МБ — ограничение платформы).

### Ответы (reply)

Если пересылаемое сообщение — ответ на другое, пересланная копия оформляется как
ответ на пересланную копию оригинала. Для этого на каждую пересылку сохраняется
соответствие «id оригинала ↔ id копии» в таблице `message_links` (обе стороны).
При пересылке ответа `MessageRelayService` находит по этой карте копию исходного
сообщения в целевом чате и проставляет reply: Telegram — `ReplyParameters`,
MAX — `link{type:"reply", mid}`. Если оригинал не найден в карте (отправлен до
связки/фичи) — сообщение пересылается как обычное, без оформления ответа.
Ограничение: для голоса/аудио MAX (см. выше про пустой `message_created`) id
недоступен, поэтому ответы на такие сообщения пока не переносятся.

### Редактирование и удаление

Правки и удаления переносятся на пересланную копию через ту же карту `message_links`
(отдельная таблица не нужна) — `MessageRelayService.RelayEditAsync` / `RelayDeleteAsync`.

- **Правка.** Меняется текст, а у медиа — подпись (само медиа не заменяется). Приём:
  Telegram — апдейт `edited_message` (добавлен в `allowedUpdates`), MAX — `message_edited`.
  Отправка: Telegram — `EditMessageText`/`EditMessageCaption`; MAX — `PUT /messages`, причём
  чтобы правка подписи не стёрла вложение, текущие вложения дотягиваются через
  `GET /messages?message_ids=` и переотправляются по `token`. У MAX окно редактирования
  ограничено по времени — по его истечении правка не применится (ошибка логируется).
- **Удаление.** Работает только **MAX → Telegram**: MAX присылает `message_removed`, и мы
  удаляем копию в Telegram (`DeleteMessage`) + чистим запись карты. Обратное направление
  невозможно — Telegram **не уведомляет** ботов об удалении сообщений пользователем.
- Собственные правки/удаления бота игнорируются (та же защита от эха по `_botId`), поэтому
  цикла не возникает.

### Форматирование

Разметка текста (жирный, курсив, подчёркнутый, зачёркнутый, моноширинный,
ссылки) переносится между платформами через платформо-независимую модель
`FormattedText` (чистый текст + список участков `TextSpan` с офсетами в UTF-16):

- **Приём.** Каждый `*BotService` конвертирует свой формат в `FormattedText`:
  Telegram — из `MessageEntity[]` (`TelegramFormatting`), MAX — из массива
  `markup` (`MaxFormatting`).
- **Отправка.** Целевой клиент кодирует `FormattedText` в свой формат:
  Telegram — обратно в entities (без `parse_mode`, без экранирования),
  MAX — в markdown-строку с `format: "markdown"` (спецсимволы экранируются).

Стили, у которых нет пары на другой стороне (spoiler/blockquote/mention у
Telegram; heading/highlighted/user_mention у MAX), при переносе отбрасываются —
текст остаётся, стиль теряется. Само форматирование по разметке (`FormattedText`)
не зависит от `*BotService`, как и весь `MessageRelayService`.

Сообщения от ботов вообще (не только от своего, но и от любых чужих ботов в
чате) не пересылаются — это решает каждый `*BotService` сам, до вызова
`MessageRelayService`, по данным конкретной платформы об отправителе
(`message.From.IsBot` в Telegram, `message.Sender.IsBot` в MAX — nullable,
т.к. неизвестно, всегда ли MAX присылает этот признак).

### Видео из ссылок

Опциональное дополнение к пересылке (`Services/VideoEmbed`, `VideoEmbedRelayService`):
если в пересылаемом сообщении есть ссылка на YouTube-видео или Shorts, бот дополнительно
скачивает само видео через внешний сервис-загрузчик и публикует его отдельным сообщением
(видео + текст ссылки + от кого) в **оба** чата связки — и в тот, откуда пришло сообщение,
и в связанный, — чтобы видео можно было посмотреть, не переходя по ссылке ни там, ни там.

- **Кодирование ссылки в файл** делает отдельный сервис (исходники и протокол — см.
  `c:\sync_video\docs`, особенно `AI_CONTEXT.md`): `POST /api/v1/tasks {url}` ставит
  задачу в очередь, дальше нужно поллить `GET /api/v1/tasks/{taskId}`, пока статус не
  станет `completed`/`failed`, и только тогда скачать файл по `downloadUrl`. Адрес и
  параметры — `VideoEmbed:BaseUrl`/`ApiKey`/`PollIntervalSeconds`/`MaxWaitSeconds`.
  Пустой `BaseUrl` отключает функцию целиком.
- **Включена по умолчанию**, но управляется **per-связке** (`chat_links.video_embed_enabled`,
  миграция M010) — выключить можно из мини-приложения, в карточке связки.
- Ссылка ищется в исходном (не промодерированном) тексте сообщения — и в самом тексте, и
  в участках разметки `TextSpanKind.Link` (когда видимый текст ссылки не совпадает с URL);
  берётся первая найденная (`YouTubeLinkExtractor`).
- Запускается **в фоне**, не блокируя саму пересылку: скачивание видео может занимать от
  секунд до нескольких минут (очередь на сервисе, скачивание, конвертация), а апдейты
  каждый `*BotService` обрабатывает последовательно — ждать здесь значило бы задерживать
  обработку следующих сообщений. Фоновая задача использует токен отмены уровня приложения
  (`IHostApplicationLifetime.ApplicationStopping`), а не токен вызывавшего апдейта: в
  режиме Webhook это `HttpContext.RequestAborted`, который отменяется вскоре после ответа
  на сам HTTP-запрос — обрывать им долгую задачу нельзя.
- Любая неудача (сервис не настроен/недоступен, ссылка не распознана сервисом, видео
  приватное/слишком длинное/большое, не дождались за `MaxWaitSeconds`) — не ошибка
  пересылки: сообщение с текстом ссылки уже ушло своим чередом, видео просто не
  добавляется, причина уходит в лог.

## Модерация

Всё, что уходит в связанный чат, проходит через `ModerationService` — единую точку перед
отправкой. Проверяются и обычные сообщения, и правки: иначе запрет обходился бы отправкой
безобидного текста с последующей правкой на запрещённый. Пока проверяется только текст.

Проверка многослойная: сначала текст приводится к единой форме, затем к нему применяются
правила.

### Слой 1: приведение к единой форме

Без него фильтр обходится тривиально — «ХУЙ», «хуууй», «х.у.й», «xyй» (латинские `x` и `y`),
«ху​й» (с невидимым пробелом внутри) для наивного сравнения шесть разных строк.
`TextNormalizer` приводит их к одной:

1. **NFKD** — раскладывает совместимые и составные символы: `ﬁ` → `fi`, `４` → `4`,
   `𝗑` → `x`, `é` → `e` + акут, `й` → `и` + кратка, `ё` → `е` + умлаут.
2. **Отбрасываются диакритика и невидимые символы** — то, что осталось от разложения, плюс
   пробел нулевой ширины, мягкий перенос, метки направления письма. Их вставляют внутрь
   слова именно ради обхода фильтров.
3. **Замена визуальных двойников** (`Confusables`). Это ключевой шаг, и обычной
   юникод-нормализации для него **не хватает принципиально**: NFKC/NFKD работают внутри
   одного набора символов и кириллическую `а` (U+0430) к латинской `a` (U+0061) не приводят
   — это разные буквы, а не разные записи одной. Схлопывание межалфавитных подмен описано
   отдельно, в [UTS #39](https://www.unicode.org/reports/tr39/) (алгоритм skeleton и файл
   `confusables.txt`). У нас не весь `confusables.txt` (~6500 записей), а выборка под задачу:
   латиница, греческий, «экзотическая» кириллица и цифро-символьные замены (`0`→`о`,
   `3`→`з`, `@`→`а`).
4. **Нижний регистр** и **схлопывание повторов**: «хуууй» → «хуй».
5. Внутри слова отбрасываются знаки препинания: «х.у.й», «б*л*я*д*ь».

Через ту же нормализацию проходят и словари — поэтому вписывать в них варианты с латинскими
буквами или цифрами вместо букв не нужно.

**Про смешение алфавитов.** Заглавные латинские `B, H, K, M, T` неотличимы от кириллических
`В, Н, К, М, Т`, а их строчные формы — уже нет. Если заменять их всегда, одно и то же
английское слово нормализуется по-разному в зависимости от регистра (`bitch` и `BITCH`
разойдутся), и со словарём совпадёт только одно. Поэтому такие замены применяются лишь к
словам, где латиница соседствует с кириллицей: смешение алфавитов внутри слова само по себе
признак подмены (mixed-script detection, там же в UTS #39). «MУДАК» с латинской `M` —
подмена, «BITCH» целиком латиницей — обычное английское слово.

### Слой 2: запрещённое законом

Наркотики и спам. Такие сообщения **не пересылаются** — вместо них уходит заглушка:

```
👤 Имя · (из TG)
🚫 Нам показалось, что сообщение возможно нарушает законы РФ, мы рисковать не будем
и вам не советуем. Смотрите оригинал сообщения в другом мессенджере.
```

Причина в заглушке не называется — сообщать «у вас нашли наркотики» человеку, чью фразу
фильтр понял неправильно, хуже, чем нейтральная формулировка. Причина остаётся в журнале.

Словарь двухуровневый, потому что почти весь «сигнальный» словарь наркотемы состоит из
обычных русских слов — «соль», «скорость», «шишки», «клад», — и блокировать по одному
такому значит рубить нормальную переписку:

| Уровень | Что там | Когда срабатывает |
|---|---|---|
| Strong | названия веществ («мефедрон», «амфетамин») и однозначные зазывалки («быстрый заработок») | одного совпадения достаточно |
| Weak | само по себе безобидное («соль», «закладки», «доход», «инвестиции») | 2 разных слова для наркотиков, 3 для спама |

Порог у спама выше: «доход», «прибыль», «инвестиции» — обычные слова деловой переписки.

Спамовый strong-список — это **целые формулировки**, а не отдельные слова, и так и должно
быть: одного совпадения хватает для блокировки, поэтому запись должна быть такой, какая в
живой переписке не встречается. «Заработок» — обычное слово, «заработок без вложений» — уже
зазывалка. Покрыты заработок и «схемы», инвестиции и криптовалюта, казино и ставки, серые
финансовые услуги (обнал, дропы, кредиты), накрутка, поддельные документы, пробив и взлом,
фишинговые «выигрыши», интим-услуги.

При пополнении списка есть два неочевидных правила:

- **Не писать варианты через «е»/«ё» и с «й»** — нормализация сводит их к одному виду
  («лёгкий» и «легкий» после неё неразличимы), лишние записи отсеет `Distinct`.
- **Не вставлять числа.** Нормализация схлопывает подряд идущие одинаковые символы, поэтому
  «1000», «100» и «10» превращаются в одно и то же: фраза «доход от 1000» начала бы ловить
  безобидное «доход от 10». Числа выражать словами — «тысяч в день».

### Слой 3: мат

Сообщение пересылается, но бранные слова маскируются: остаётся первая буква, остальные
заменяются звёздочками — «хуй» → «х**». Звёздочки ставятся только вместо букв и цифр, знаки
препинания остаются на месте («хуй!» → «х**!»). В «шапку» добавляется отметка:

```
👤 Имя · (из TG) [изменено ботом]
```

**Длина слова при маскировке сохраняется** — это не косметика: от неё зависят офсеты
участков форматирования (`FormattedText.Spans`), и при замене символ-в-символ жирный или
курсивный кусок текста не съезжает.

Мат ищется как подстрока в слове — так ловятся приставки и окончания («за-хуя-рил»,
«пизд-ец») без перечисления всех форм. Обратная сторона — ложные срабатывания на обычных
словах, внутри которых оказался корень: «страхуй», «команда», «требует», «барсука»,
`shiitake`. Они перечислены в списке исключений, и **пополнение этого списка — нормальный
рабочий процесс**: ложное срабатывание лечится добавлением слова туда, а не ослаблением корня.

Словари (мат, исключения, наркотики, спам) лежат в одном файле
[`Services/Moderation/ModerationDictionary.cs`](src/SyncMax/Services/Moderation/ModerationDictionary.cs)
обычными строками — пополнять их можно, не разбираясь в остальном коде.

### Что этот слой пока не ловит

- **Пробелы между буквами**: «х у й». Склеивать слова обратно нельзя без риска — «страх уйти»
  превратилось бы в срабатывание.
- **Транслит**: «hui», «blyat». Лечится дописыванием форм в словарь.
- **`3` в английских словах**: цифра отдана русской «з» по начертанию, поэтому «sh3t» проходит.
  Однозначной посимвольной замены здесь не существует — одна цифра не может означать сразу
  две разные буквы.

## Системные команды

Обрабатываются только в личном чате с ботом (не в группе/канале), в обоих
мессенджерах одинаково — логика вынесена в `SystemCommandService`.

- `/app` — присылает сообщение с кнопкой, открывающей [мини-приложение](#мини-приложение).
  Если `MiniApp:Url` не задан — придёт просто текст, без кнопки.
- `/deleteAllLinks` — удаляет все связки чатов (`chat_links`), у всех пользователей.
- `/clear` — удаляет все связки чатов, а также связку аккаунтов и "ожидающий"
  выбор чата (`linked_to_user`, `linking_chat_id`, `linking_chat_type`,
  `linking_chat_title`) у обеих сторон связки, если аккаунты были связаны.
  Вместе со связкой удаляется и общий [аккаунт](#база-данных) пары.
  Обеим сторонам приходит сообщение о сбросе настроек, а затем — новое
  приглашение связать аккаунты (как после `/start`).

## Мини-приложение

Веб-интерфейс, который открывается прямо из чата с ботом — **один и тот же для MAX и
Telegram**. Через него видно свои связки чатов, можно включить/выключить пересылку,
сменить направление, удалить связку и связать аккаунты. Разделы в нижнем меню:
**Связки**, **Статистика**, **Поддержка** (работают), **Подписка** (пока заглушка).

Раздаётся тем же процессом, что и webhook-эндпоинты: статика — из `wwwroot/app` по пути
`/app`, API — `/api/miniapp/*`. Отдельный сервер или контейнер не нужен.

### Почему бэкенд общий

Мини-приложения MAX и Telegram устроены почти одинаково, и главное — **схема подписи
данных запуска совпадает буквально**:

```
secret = HMAC-SHA256(key: "WebAppData", data: токен бота)
hash   = hex(HMAC-SHA256(key: secret, data: launch_params))
```

где `launch_params` — пары `ключ=значение` из `initData` (кроме самого `hash`),
отсортированные по ключу и склеенные через `\n`. Различается только токен, которым
подписано, и набор необязательных полей (у MAX — `chat`, `ip`; у Telegram — `chat_type`,
`chat_instance`). Поэтому проверка живёт в одном классе `WebApp/MiniAppAuth` на обе
платформы, а различия на фронте сведены к одному файлу `wwwroot/app/js/platform.js`:
Telegram кладёт мост в `window.Telegram.WebApp`, MAX — в `window.WebApp`.

Из моста берутся только данные запуска, палитра оформления и системные мелочи (кнопка
«Назад», тактильная отдача, открытие ссылок). **Диалоги подтверждения — свои, в HTML**
(`js/dialog.js`): у `showConfirm`/`showAlert` разный вид у MAX и Telegram, а в браузере
вместо них появляется штатный `confirm` — три площадки, три разных окна. Своё окно даёт
один и тот же вид везде, как и весь остальной интерфейс.

Строка `initData` передаётся заголовком `Authorization: TmaAuth {tg|max} {initData}` и
проверяется на **каждом** запросе — своих сессий и токенов у приложения нет. Просроченные
данные (`auth_date` старше `MiniApp:AuthMaxAgeHours`, по умолчанию сутки) отклоняются.

Пользователь видит и меняет только те связки, где стороной записан он сам или его
связанный аккаунт; на чужой `id` API отвечает `404` (не `403` — иначе перебором можно
было бы выяснить, какие связки вообще существуют).

### Настройка

```json
{
  "MiniApp": {
    "Url": "https://ваш-домен/app",
    "AuthMaxAgeHours": 24,
    "DevUserId": "",
    "DevUserMessenger": "tg"
  }
}
```

- `Url` — публичный адрес приложения, **только https** (иначе Telegram не примет кнопку
  `web_app`). Пусто — кнопки запуска не выставляются, но сама страница по `/app` всё равно
  отдаётся.
- `DevUserId`/`DevUserMessenger` — **только для отладки**: пока `DevUserId` не пуст, API
  принимает запросы без подписи и работает от имени этого пользователя, что позволяет
  открыть `/app` в обычном браузере. В рабочей конфигурации должно быть пусто; на старте
  в лог пишется предупреждение.

### Как приложение попадает к пользователю

**Telegram** — обоими способами сразу, ничего вручную настраивать не нужно:
- постоянная кнопка рядом с полем ввода — бот сам вызывает `setChatMenuButton` при старте,
  если задан `MiniApp:Url`;
- команда `/app` — сообщение с inline-кнопкой `web_app`.

**MAX** — основной путь через кабинет: [business.max.ru](https://business.max.ru) →
**Чат-боты** → **Расширенные настройки** → вставить `Url` и выбрать надпись на кнопке.
После этого кнопка запуска появляется в чате с ботом сама. Команда `/app` дополнительно
присылает сообщение с inline-кнопкой `open_app`.

> Формат кнопки `open_app` публично не задокументирован (как и `POST /subscriptions`,
> см. ниже) и заполнен по типовому шаблону — если MAX его не примет, клиент это заметит,
> напишет в лог и переотправит сообщение **без кнопки**, так что ничего не сломается.
> Править в этом случае нужно только `MaxButton` в `MaxModels.cs` и
> `MaxApiClient.SendMiniAppButtonAsync`.

## Приём обновлений: long polling / webhook

У каждого мессенджера свой независимый режим приёма обновлений —
`Telegram:Mode` / `Max:Mode`, значения `LongPolling` (по умолчанию) или `Webhook`.
Можно держать один мессенджер на polling, а другой на webhook — режимы не связаны.

- **LongPolling** (по умолчанию) — бот сам опрашивает сервер мессенджера в цикле.
  Публичный адрес не нужен, работает и локально за NAT.
- **Webhook** — мессенджер сам присылает обновления HTTP-запросом на публичный
  HTTPS-адрес. Требует, чтобы сервер был доступен снаружи (напр. за reverse proxy
  с TLS-терминацией — Kestrel слушает `HttpServer:ListenUrl` уже без TLS, обычно
  `http://127.0.0.1:PORT` за nginx, либо напрямую `http://0.0.0.0:PORT`, если TLS
  терминируется иначе).

Адрес прослушивания один на всех (`HttpServer:ListenUrl`) — HTTP-сервер в процессе
один. Всё, что относится к конкретному боту (публичный адрес и путь), лежит в его
собственной секции `Telegram:Webhook` / `Max:Webhook`:

```json
{
  "Telegram": {
    "Token": "ВАШ_TELEGRAM_BOT_TOKEN",
    "Mode": "Webhook",
    "Webhook": {
      "Url": "https://ваш-домен/webhook/telegram",
      "Path": "/webhook/telegram"
    }
  },
  "Max": {
    "Token": "ВАШ_MAX_BOT_TOKEN",
    "Mode": "Webhook",
    "Webhook": {
      "Url": "https://ваш-домен/webhook/max",
      "Path": "/webhook/max"
    }
  },
  "HttpServer": {
    "ListenUrl": "http://0.0.0.0:8443"
  }
}
```

- `HttpServer:ListenUrl` — общий адрес, на котором Kestrel принимает входящие
  webhook-запросы обоих ботов.
- `Url` — публичный адрес, который регистрируется в самом мессенджере
  (Telegram — `setWebhook`, MAX — `POST /subscriptions`); должен указывать на
  `Path` этого же мессенджера через ваш reverse proxy/домен.
- `Path` — локальный путь, который слушает Kestrel (должен совпадать с путём
  в `Url`). По умолчанию — `/webhook/telegram` и `/webhook/max`.

**Отдельного секрета в конфиге нет:** подлинность входящих запросов проверяется
по токену самого бота (`Telegram:Token` / `Max:Token`) — у каждого бота свой,
и мессенджер его уже знает. Передаётся не сам токен, а его SHA-256
(`WebhookSecret`): Telegram разрешает в `secret_token` только `A-Z a-z 0-9 _ -`
(а в токене есть двоеточие), у MAX же секрет уходит query-параметром в url
подписки — настоящий токен API там светился бы в логах reverse proxy. Telegram
возвращает секрет заголовком `X-Telegram-Bot-Api-Secret-Token`, MAX — параметром
`?token=`; запрос с чужим значением отклоняется (`401`).

HTTP-сервер поднимается **всегда, когда задан `HttpServer:ListenUrl`** —
независимо от режимов ботов. Если `ListenUrl` пуст, Kestrel слушает случайный
порт на `127.0.0.1` и наружу ничего не открывается. Webhook-эндпоинт каждого
бота при этом маппится только в его режиме `Webhook`.

### Проверка доступности

`GET /test` отвечает `200` и текстом `ok` — всегда, независимо от режимов ботов.
Удобно проверить, что порт открыт и reverse proxy настроен верно:

```
curl https://ваш-домен/test
ok
```

При переключении Telegram с webhook обратно на `LongPolling` бот сам вызывает
`deleteWebhook` при старте (иначе `getUpdates` конфликтует с активным webhook).

Формат эндпоинта подписки MAX (`POST /subscriptions`) не задокументирован
публично на момент реализации — заполнен по типовому шаблону Bot API (см.
комментарий в `MaxModels.cs`/`MaxApiClient.SubscribeWebhookAsync`); если
реальный API отличается, поправить нужно только эти два места.

## Ключи / токены

Оставлены пустыми в [`src/SyncMax/appsettings.json`](src/SyncMax/appsettings.json) — впишите свои:

```json
{
  "Telegram": { "Token": "ВАШ_TELEGRAM_BOT_TOKEN" },
  "Max":      { "Token": "ВАШ_MAX_BOT_TOKEN", "ApiBaseUrl": "https://platform-api2.max.ru" }
}
```

Токены можно не хранить в файле, а передать через переменные окружения
(перекрывают `appsettings.json`). Имя переменной — это путь настройки, где `:`
заменено на `__`, поэтому так передаётся **любая** настройка, а не только токены:

```
Telegram__Token=...
Max__Token=...
Telegram__Webhook__Url=https://example.com/webhook/telegram
Database__ConnectionString=Data Source=/data/syncmax.db
```

Если токен мессенджера пуст — соответствующий бот просто не запускается
(приложение работает, это удобно для локальной отладки одного из ботов).

## Запуск в Docker

Готовые [`Dockerfile`](Dockerfile) и [`docker-compose.yml`](docker-compose.yml) — в
корне репозитория. Образ собирается из исходников (multi-stage: `sdk:10.0` → `aspnet:10.0`)
и уже содержит `ffmpeg`, так что ставить на хост .NET SDK не нужно.

### Быстрый старт

```bash
cp .env.example .env      # PowerShell: Copy-Item .env.example .env
# впишите в .env токены Telegram__Token и Max__Token
docker compose up -d --build
docker compose logs -f
```

### Как передаются настройки

Единственный источник конфигурации для контейнера — файл **`.env`** рядом с
`docker-compose.yml` (шаблон со всеми ключами и комментариями — [`.env.example`](.env.example)).
Локальный `appsettings.json` в образ **не** попадает (исключён в `.dockerignore`),
чтобы рабочие токены не запеклись в слои образа.

Имена переменных — те же пути настроек с разделителем `__`:

```
Telegram__Token=123456:AA...
Max__Token=f9LHod...
Telegram__Mode=Webhook
Telegram__Webhook__Url=https://example.com/webhook/telegram
```

Отсюда следует, что в `.env` можно положить любую настройку из `appsettings.json`,
даже если её нет в шаблоне. Приоритет обычный: `.env` > `ENV` образа > дефолты в коде.

Отдельно в `.env` лежат два параметра для самого compose (в приложение они не идут):
`HTTP_PORT` — порт на хосте, `TZ` — часовой пояс контейнера (влияет на время в логах
и суточную ротацию файлов).

Если конфигурацию удобнее держать одним JSON, а не набором переменных, — положите
рядом `appsettings.docker.json` и раскомментируйте в `docker-compose.yml` строку
монтирования его в `/app/appsettings.Production.json`.

### Данные и логи

Смонтированы каталогами на хосте, поэтому переживают пересборку образа и `docker compose down`:

| В контейнере | На хосте | Что там |
|---|---|---|
| `/data/syncmax.db` | `./data/` | база SQLite |
| `/app/logs/` | `./logs/` | `syncmax-YYYY-MM-DD.log` |

Если база уже есть локально — просто положите файл в `./data/syncmax.db` до первого
запуска, миграции подхватят её и при необходимости обновят схему.

На Linux контейнер работает под непривилегированным пользователем `app` (uid 1654).
Если он не сможет писать в смонтированные каталоги, выполните на хосте
`sudo chown -R 1654:1654 data logs` либо задайте свой `user:` в `docker-compose.yml`
(строка с примером закомментирована в конце файла). На Docker Desktop (Windows/macOS)
этого не требуется.

### Webhook и порт

Порт `8443` внутри контейнера проброшен на `HTTP_PORT` хоста. Он нужен только при
`Mode=Webhook`; для `LongPolling` проброс можно закомментировать. Сам контейнер слушает
**HTTP** — TLS-сертификат для публичного адреса из `*__Webhook__Url` терминирует
reverse proxy (nginx/Caddy/Traefik) перед ним.

Проверить, что контейнер доступен снаружи: `curl https://ваш-домен/test` → `ok`. Этот же
эндпоинт используется в `HEALTHCHECK`, поэтому состояние видно и в `docker compose ps`.

### Частые команды

```bash
docker compose up -d --build     # пересобрать и перезапустить после правок кода
docker compose restart           # перечитать .env
docker compose logs -f --tail=100
docker compose down              # остановить (данные в ./data остаются)
```

## Логирование

Логи пишутся одновременно в **консоль** (стандартный провайдер хоста) и в **файл**
через собственный `FileLoggerProvider` (без внешних зависимостей). Файлы — в подпапке
`logs` рядом с бинарником, с ротацией по дням: `logs/syncmax-YYYY-MM-DD.log`.

Уровни берутся из секции `Logging:LogLevel` в `appsettings.json` (общие для консоли и
файла). При необходимости для файла можно задать отдельные уровни через алиас `File`,
например:

```json
"Logging": {
  "LogLevel": { "Default": "Information" },
  "File": { "LogLevel": { "Default": "Warning" } }
}
```

## База данных

SQLite, файл создаётся автоматически. Путь задаётся в `Database:ConnectionString`:
локально — абсолютный путь (`C:\sync_max\data\syncmax.db`), в контейнере —
`/data/syncmax.db` (каталог `./data` на хосте). Путь лучше держать абсолютным:
относительный (`Data Source=syncmax.db`) резолвится от текущей рабочей директории
процесса, а она разная при запуске из Visual Studio и напрямую из `bin\Debug\...` —
получаются две разные базы.

**Таблица `users`** — по записи на каждый мессенджер:
`user_id` (open_id для MAX), `messenger` (`tg`/`max`), `registered_at`,
`is_active`, `name`, `language`, `link_code`, `link_code_created_at`,
`linked_to_user`, `account_id`, `linking_chat_id`, `linking_chat_type`,
`linking_chat_title`. Первичный ключ — пара (`user_id`, `messenger`). Индексы:
`ix_users_link_code` — поиск по коду связки, `ix_users_account_id` — участники аккаунта.

Связка аккаунтов хранится прямо в этой таблице: `linked_to_user` — `user_id`
связанного аккаунта в другом мессенджере, заполняется у обеих сторон связки.
`linking_chat_*` — "ожидающий" выбор чата для связки чатов (репост сделан
одной стороной, ждём вторую); очищается, как только связка создана.

**Таблица `accounts`** — пара связанных пользователей (MAX + Telegram), то есть одна
физическая персона: `id`, `created_at`. Своих данных пока не несёт — она нужна как
общая точка привязки для всего, что относится к паре целиком, а не к отдельному
мессенджеру (статистика, в перспективе подписка).

Аккаунт живёт ровно столько, сколько живёт связка: создаётся в момент связывания
двух мессенджеров и удаляется при её разрыве (`/clear`, кнопка в мини-приложении).
Обе операции — по одной транзакции на всю пару, `UserRepository.LinkAccountsAsync` и
`UserRepository.UnlinkAsync`; разрыв симметричен, вызова с одной стороны достаточно.

`users.account_id` объявлена с `ON DELETE SET NULL`, поэтому удаление строки
`accounts` само обнуляет ссылки у обеих сторон. Таблицы, которые появятся позже,
должны ссылаться на аккаунт с `ON DELETE CASCADE` — тогда тот же самый `DELETE`
уберёт и их записи, отдельная уборка не понадобится. Связкам, созданным до миграции
`M007`, аккаунты заведены ею же; односторонние связки (`A → B`, но `B` не ссылается
на `A`) при этом пропущены и остаются с `account_id IS NULL`.

**Таблица `chat_links`** — связки чатов/каналов между MAX и Telegram:
`max_chat_id`, `max_chat_type` (`chat`/`channel`), `max_user_id`,
`tg_chat_id`, `tg_chat_type`, `tg_user_id`, `active`, `title`
(`{чат1} <=> {чат2}`), `max_chat_title`, `tg_chat_title`,
`repost_type` (`max_to_tg`/`tg_to_max`/`both`, см.
[Направление пересылки](#направление-пересылки)), `created_at`. Уникальность по паре
(`max_chat_id`, `tg_chat_id`).

Названия чатов хранятся дважды: `title` — общая склейка для сообщений бота, а
`max_chat_title`/`tg_chat_title` — по сторонам. Порядок имён в `title` зависит от того,
кто из двоих сделал репост первым, поэтому определить по нему, где MAX, а где Telegram,
нельзя — а мини-приложению это нужно, чтобы показать направление пересылки. Колонки по
сторонам добавлены миграцией `M005` и у более старых связок пусты (интерфейс тогда
показывает общий `title`).

**Таблица `relay_stats`** — статистика пересылки: `account_id`, `chat_link_id`, `day`
(`YYYY-MM-DD`, UTC), `direction` (`max_to_tg`/`tg_to_max`), `messages`, `text_bytes`
и по четыре пары счётчиков «штук/байт» на виды вложений (`photo_*`, `video_*`,
`audio_*`, `file_*`), `updated_at`. Первичный ключ — (`account_id`, `chat_link_id`,
`day`, `direction`).

Хранятся только **дневные** строки: месяцы и суммы за всё время считаются из них
(`GROUP BY substr(day, 1, 7)`). Отдельные таблицы месяцев и итогов пришлось бы держать
в согласии с днями, а выигрыша не дают — строк здесь единицы на связку в день.

`chat_link_id` намеренно без внешнего ключа: с `ON DELETE SET NULL` он сломал бы
первичный ключ, так как в SQLite NULL не равны друг другу и строки удалённых связок
перестали бы схлопываться. Поэтому id хранится как историческое значение — связку могли
удалить, но её вклад в сумму аккаунта остаётся (в интерфейсе — «Удалённая связка»).
Уборка идёт каскадом по `account_id`: разрыв связки аккаунтов уносит и статистику.

**Таблица `message_links`** — карта «оригинал ↔ пересланная копия» для переноса
ответов (reply): `max_chat_id`, `max_msg_id` (mid), `tg_chat_id`, `tg_msg_id`
(message_id), `created_at`. По одной записи на пересылку; индексы по обеим
сторонам — поиск копии работает в любом направлении, плюс индекс по `created_at`
для фоновой уборки (см. ниже).

### Как считается статистика

Показатели снимаются в одной точке — `MessageRelayService`, сразу после успешной отправки
в связанный чат. Объём берётся как размер уже скачанных временных файлов вложений, поэтому
он платформо-независим и не требует запросов к API. Правки и удаления не считаются;
заблокированное модерацией сообщение считается сообщением без трафика (заглушка ушла).

Запись **не идёт на каждое сообщение**: пересылка только прибавляет счётчики в памяти
(`RelayStatsCollector` — `GetOrAdd` плюс `Interlocked.Add`, без ввода-вывода и блокировок),
а на диск накопленное уходит пачкой раз в `Stats:FlushIntervalMinutes` минут одной
транзакцией (`RelayStatsFlushService`). Иначе транзакция на каждое сообщение заставляла бы
пересылку соревноваться за единственную в SQLite блокировку записи.

```json
"Stats": {
  "FlushIntervalMinutes": 5,
  "StartupDelaySeconds": 30
}
```

Отсюда следствие: при аварийном завершении процесса теряется накопленное с прошлой
выгрузки — статистика справочная, и такой размен осознан. При штатной остановке делается
последняя выгрузка, а если транзакция не удалась (база занята), снятые показатели
возвращаются в накопитель и уезжают следующим проходом.

Выгрузку инициирует не только фоновый сервис: экран статистики мини-приложения зовёт её
сам, перед чтением (`RelayStatsWriter` — общий для обоих). Иначе между двумя фоновыми
проходами показатели жили бы только в ОЗУ, и пользователь, переславший сообщение минуту
назад, видел бы пустой экран и решал, что статистика не работает. На горячий путь это не
влияет: экран открывают несравнимо реже, чем пересылают сообщения, а сама пересылка
по-прежнему не пишет в БД.

Суммы за месяц и за всё время считаются на лету из дневных строк, ключ группировки —
`substr(day, 1, 7)`. Направление в статистике — факт переноса (`max_to_tg`/`tg_to_max`),
а не настройка связки: у `both` считается та сторона, в которую сообщение реально ушло.

### Уборка старых записей

`message_links` растёт по записи на каждое пересланное сообщение и сама не
самоочищается: записи убираются только при удалении сообщения или связки. Хранить их
дольше пары недель незачем — карта нужна, пока на сообщение ещё могут ответить или
отредактировать его. Поэтому в приложении работает фоновый сервис
`MessageLinkCleanupService`, удаляющий записи старше `Cleanup:MessageLinkRetentionDays`
(по умолчанию 14 суток).

Удаление идёт **партиями с паузами**, а не одним запросом: в ту же таблицу пишет
пересылка сообщений, а блокировка записи в SQLite одна на всю базу — разовый `DELETE`
по десяткам тысяч строк придержал бы её заметное время. Маленькие транзакции с паузами
освобождают базу после каждой партии, и записи уходят примерно так же постепенно, как
и появляются.

```json
"Cleanup": {
  "MessageLinkRetentionDays": 14,   // 0 — уборка отключена
  "BatchSize": 200,                 // записей за одну транзакцию
  "BatchPauseSeconds": 5,           // пауза между партиями, пока есть что удалять
  "IdlePauseMinutes": 60,           // пауза после того, как всё вычищено
  "StartupDelaySeconds": 60         // не мешаем запуску ботов и миграциям
}
```

Отбор просроченных записей опирается на индекс `ix_message_links_created_at`
(миграция `M006`), причём подзапрос сортируется по `created_at`, а не по `id`: с
сортировкой по `id` планировщик SQLite вместо индекса сканирует таблицу по rowid, и
каждый холостой проход перебирал бы её целиком.

### Миграции / версии схемы

Версия схемы хранится в `PRAGMA user_version` файла БД. При старте
`MigrationRunner` применяет все миграции с версией больше текущей в одной
транзакции каждая. Чтобы добавить изменение в будущем:

1. Создайте класс `M00X_Описание : IMigration` с бОльшим `Version`.
2. Зарегистрируйте его в `Program.cs` рядом с `M001_InitialSchema`.

Ничего вручную запускать не нужно — обновление происходит на старте.
