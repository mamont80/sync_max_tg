# SyncMax — заметки для агента

Бот-мост между MAX и Telegram. Общее описание проекта, установка, конфигурация,
Docker, БД — всё в [README.md](README.md). Здесь — только то, что нужно именно
для работы с кодом: команды и внутренние конвенции.

## Сборка / запуск

```powershell
dotnet build SyncMax.sln
dotnet run --project src/SyncMax
```

Тестового проекта в решении нет — автоматических тестов не запустить.

Единственный проект — `src/SyncMax/SyncMax.csproj`, `net10.0`. Локальная БД
(`Database:ConnectionString` в `appsettings.json`) должна быть абсолютным
путём: относительный резолвится от текущей рабочей директории процесса, а она
разная при запуске из Visual Studio и из `bin\Debug\...`.

## Устройство кода

- **Приём и отправка разделены.** `*ApiClient` (`MaxApiClient`, `TelegramApiClient`)
  реализуют общий `IMessengerApiClient` и отвечают только за исходящие запросы
  к API. `*BotService` (`MaxBotService`, `TelegramBotService`) — фоновые сервисы,
  которые занимаются только приёмом (long polling/webhook) и разбором входящих
  обновлений; для отправки сами по себе никому, кроме себя, не нужны.
- `LinkingService` не зависит ни от платформы, ни от `*BotService` — только от
  `IMessengerApiClient` (все реализации приходят через DI, нужная выбирается по
  `MessengerType`). Добавление нового мессенджера = новый `*ApiClient` (реализует
  `IMessengerApiClient`) + новый `*BotService` для приёма.
- Платформо-независимые модели — `FormattedText`/`TextSpan` (разметка),
  `RelayMessage`/`MediaAttachment` (медиа) и `ForwardOrigin` (источник репоста). Вся логика
  пересылки в `MessageRelayService` работает только с ними, не зная деталей конкретной
  платформы. «Шапка» вынесена в `Services/RelayHeader` — чистое форматирование, которое
  удобно проверять отдельно; она возвращает `FormattedText`, а не строку, потому что несёт
  ссылку на оригинал репоста.
- **Мини-приложение.** Бэкенд — `WebApp/` (`MiniAppAuth` — проверка `initData`,
  `MiniAppEndpoints` — `/api/miniapp/*`, DTO) плюс `Services/MiniAppService` со всей
  логикой и проверкой прав; эндпоинты тонкие. Фронт — статика `wwwroot/app` без сборки
  (ES-модули, ни node, ни зависимостей). Схема подписи данных запуска у MAX и Telegram
  одинаковая (`HMAC-SHA256` с ключом `"WebAppData"` от токена бота), поэтому проверка
  одна на обе платформы — различаются только токен и набор полей. На фронте вся разница
  между платформами живёт в `wwwroot/app/js/platform.js` (`window.Telegram.WebApp` против
  `window.WebApp`); остальной код платформу не видит. Интерфейс **только на русском**,
  i18n во фронтенде нет; `Services/Localization.cs` — про сообщения бота в чате, не про веб.
- **Диалоги — свои** (`wwwroot/app/js/dialog.js`: `confirmDialog`, `alertDialog`, `toast`),
  системные `showConfirm`/`showAlert` моста намеренно не используются: их вид отличается
  у MAX, Telegram и браузера, а интерфейс должен быть одинаковым. Кнопка «Назад» —
  через `platform.pushBackHandler` (стек), потому что диалог открывается поверх листа и
  должен перехватывать «Назад» первым.
- **Модерация** — `Services/Moderation`. `ModerationService` — единственная точка, через
  которую проходит всё отправляемое; вызывается из `MessageRelayService` и для сообщений,
  и для правок. Новые проверки (медиа, ссылки) добавляются внутрь него, не трогая relay.
  Ключевое в `TextNormalizer`/`Confusables`: одного NFKC/NFKD **недостаточно** — он не
  схлопывает межалфавитные подмены (кириллическая `а` не станет латинской `a`), для этого
  нужна таблица confusables из UTS #39. Замена заглавных латинских `B,H,K,M,T` применяется
  только к словам смешанного алфавита, иначе `bitch` и `BITCH` нормализуются по-разному.
  Маскировка мата **обязана сохранять длину слова** — иначе поедут офсеты `FormattedText.Spans`.
  Словари — обычные строки в `ModerationDictionary.cs`; ложное срабатывание лечится
  добавлением слова в `Exceptions`, а не ослаблением корня.
- **Аккаунт (`accounts`) — это пара связанных пользователей**, а не отдельный юзер.
  Заводится в момент связки двух мессенджеров и удаляется при её разрыве; создание и
  удаление живут только в `UserRepository.LinkAccountsAsync`/`UnlinkAsync` — по одной
  транзакции на всю пару, потому что полусвязка (одна сторона знает о второй, вторая о
  ней — нет) выглядит для остального кода как обычное состояние и молча ломает логику.
  Разрыв **симметричен**: вызова с одной стороны достаточно, чтобы распалась вся пара.
  Всё, что относится к паре целиком (статистика, в перспективе подписка), вешается на
  `account_id` с `ON DELETE CASCADE` и удаляется тем же `DELETE`, что и аккаунт, —
  своей уборки такие таблицы не требуют. `users.linked_to_user` при этом остался и
  по-прежнему используется для поиска второй стороны; обе колонки выставляются и
  снимаются только в этих двух методах, поэтому разъехаться не могут.
- **Статистика пересылки** — `Services/Stats`. Съём один: `MessageRelayService` после
  успешной отправки; объём берётся из размеров временных файлов вложений (мерить надо
  ДО `finally`, там они удаляются). Запись в БД **никогда не идёт на горячем пути**:
  `RelayStatsCollector` копит в `ConcurrentDictionary` через `Interlocked.Add`, а
  `RelayStatsFlushService` раз в `Stats:FlushIntervalMinutes` сливает всё одной
  транзакцией с `INSERT ... ON CONFLICT DO UPDATE SET messages = messages + excluded.…`
  (именно прибавление: накопитель отдаёт прирост, а не итог за сутки). Снятие —
  `Interlocked.Exchange` по каждому счётчику, а не подмена словаря: при подмене терялось бы
  всё, что конкурентный поток успел прибавить между чтением ссылки и заменой. Выгрузку
  (`RelayStatsWriter`) зовёт не только фоновый сервис, но и `MiniAppService.GetStatsAsync`
  перед чтением — иначе экран, открытый между проходами, покажет пусто, хотя сообщения
  только что переслали. Хранятся
  только дневные строки, месяцы и итоги считаются `SUM`-запросом — трёх согласованных
  источников правды заводить не надо.
- **Фоновая уборка БД** — `Services/MessageLinkCleanupService` (`BackgroundService`,
  регистрируется в `Program.cs` рядом с `*BotService`): удаляет записи `message_links`
  старше `Cleanup:MessageLinkRetentionDays`. Удаление обязано идти партиями с паузами —
  блокировка записи в SQLite одна на всю базу, а в эту же таблицу пишет пересылка.
  В подзапросе отбора `ORDER BY created_at` (не `id`) — иначе планировщик игнорирует
  индекс `ix_message_links_created_at` и сканирует таблицу по rowid.
- **«Видео из ссылок» (`Services/VideoEmbed`)** — опциональное дополнение к пересылке:
  ссылка на YouTube/Shorts в сообщении вызывает докачку самого видео через внешний сервис
  (исходники и протокол — `c:\sync_video\docs\AI_CONTEXT.md`; адрес — `VideoEmbed:BaseUrl`)
  и публикацию его в оба чата связки. Порядок жёсткий и легко ломается при правках:
  `TryRelayInBackground` зовётся из `MessageRelayService` **после** `SendChatMessageAsync`
  оригинала — статусное сообщение фичи не должно оказаться в ленте раньше самого репоста.
  Место в ленте занимается сразу (`VideoEmbedStatusBoard`: «в очереди» → «скачивается 45%»),
  и готовое видео встаёт **в то же сообщение** через `TryReplaceChatMessageMediaAsync`
  (Telegram `editMessageMedia` умеет добавлять медиа и к текстовому сообщению; MAX —
  `PUT /messages` с новым вложением). Отправлять видео «когда скачается» отдельным сообщением
  нельзя: за минуты загрузки чат уходит вперёд. Если платформа замену не выполнила — видео
  уходит новым сообщением и только ПОСЛЕ этого удаляется статус (обратный порядок оставлял бы
  чат вообще без сообщения, если отправка тоже не удалась); не вышло и так — в статусном
  сообщении остаётся причина, плюс `LogError`.
  Правки статуса троттлятся (5 с и только при смене текста): опрос сервиса идёт каждые
  `PollIntervalSeconds`, а лимиты на правку есть у обеих платформ.
  Вся работа (POST задачи, поллинг статуса, скачивание файла, статусные сообщения) уходит
  в детач-таску (`_ = Task.Run(...)` — именно Run, чтобы на горячем пути не осталось даже
  начала HTTP-запроса) — иначе ожидание сервиса (секунды-минуты) блокировало бы
  последовательную обработку апдейтов в `*BotService`.
  Из-за этого таска использует токен `IHostApplicationLifetime.ApplicationStopping`, а НЕ
  токен вызвавшего апдейта: в режиме Webhook это `HttpContext.RequestAborted`, который
  отменяется вскоре после ответа на сам HTTP-запрос — им нельзя обрывать ещё идущую задачу.
  Включена по умолчанию, переключатель — per-связке (`chat_links.video_embed_enabled`).
- Миграции схемы БД — классы `IMigration` в `Data/Migrations` (`M001`, `M002`, ...),
  версия хранится в `PRAGMA user_version`. Чтобы добавить изменение схемы: новый
  класс `M00X_Описание : IMigration` с бОльшим `Version`, зарегистрировать в
  `Program.cs` рядом с `M001_InitialSchema`. Ничего вручную запускать не нужно —
  применяется на старте.

## На что обратить внимание

- **Репост в MAX приходит с пустым `body`.** Весь контент (текст, разметка, вложения) лежит
  в `link.message`, а в `body` остаются только `mid` и `text: ""`. Брать содержимое надо
  оттуда (см. `MaxBotService.BuildRelayMessageAsync`), иначе сообщение выходит пустым и
  молча отбрасывается по `relay.IsEmpty`. При этом `SourceMessageId` — по-прежнему
  `body.Mid`: карта `message_links` должна указывать на сообщение в НАШЕМ чате.
- **MAX подтверждает правку с вложением, которое не применил.** На `PUT /messages` с только
  что загруженным видео сервер отвечает 200, но если файл ещё не обработан — сообщение молча
  остаётся текстовым (при ОТПРАВКЕ тот же случай даёт 400 и ловится ретраем, при правке — нет).
  Поэтому `TryReplaceChatMessageMediaAsync` после каждого PUT перечитывает сообщение
  (`HasAttachmentsAsync`) и повторяет правку, пока вложение не появится. Без этой проверки
  статус «видео из ссылок» навсегда застревал на «отправляется…».
- **DTO и часть эндпоинтов MAX API не задокументированы публично** на момент
  реализации — `MaxModels.cs`, `MaxApiClient`, включая `SubscribeWebhookAsync`
  (`POST /subscriptions`) и кнопку `open_app` (`MaxButton`), заполнены по типовому
  шаблону Bot API. Если реальный API отличается — править нужно именно эти места
  (см. также комментарий в `MaxModels.cs`). У кнопки мини-приложения отказ сервера
  обрабатывается: сообщение переотправляется без кнопки.
- **Отладка мини-приложения в браузере.** Подписанного `initData` вне мессенджера нет,
  поэтому есть `MiniApp:DevUserId`/`DevUserMessenger`: пока они заполнены, подпись
  НЕ проверяется и запросы идут от имени этого пользователя. В рабочей конфигурации
  должны быть пустыми (на старте пишется предупреждение).
- `builder.WebHost.UseStaticWebAssets()` в `Program.cs` — не декоративный вызов: без него
  неопубликованная сборка, запущенная не в окружении `Development`, отдаёт по `/app` 404
  (`wwwroot` в `bin/` не копируется, доступен только через манифест статики).
- Для доверия TLS-цепочке `platform-api2.max.ru` в проект добавлены сертификаты
  российского Минцифры (`Certificates/russian_trusted_*.cer`, см.
  `MaxTrustedCertificates`) — при переносе/докеризации их нужно копировать вместе
  с бинарником (уже настроено в `.csproj`).
- Сообщения от собственного бота (в т.ч. пересланные им же) и от чужих ботов
  вообще — не обрабатываются повторно; это защита от зацикливания при
  `repost_type = both`, реализована в каждом `*BotService` по данным платформы
  об отправителе.
